# archetypes · 判型与默认文档集

> 读这个文件的两个时机：判项目类型（步骤 2），以及派生一个没见过的行业。

## 一、判型证据表

用 `scan --repo .` 输出的 `signals`，按下面顺序判：

| 层 | 字段 | 判什么 |
|---|---|---|
| **L1 强结构** | `signals.l1Markers` | 是否软件项目。命中 ≥2 → `software` |
| **L2 文档域** | `signals.l2DomainHits` | 哪一类行业。看**目录名**命中为主，文件名命中为辅 |
| **L3 内容抽样** | 自己抽 8–12 个 md 的 H1/H2 + 前 200 字 | 消歧（同名目录不同义），只在 L1/L2 冲突时用 |
| **L4 元信号** | `signals.names.datedNameRatio`、`mdFiles`、`topDirs`、`counts.inArchive` | 判形态、决定台账与归档的权重 |

**判定规则（写死，防乱猜）**

1. L1 命中 ≥2 → `software`。其中：有 `deploy/` 或 `docker-compose.yml`/`compose.yml` 或 多环境证据（多次提及"测试环境/生产"）→ `software-delivery`；否则 `software-lib`
2. L1 = 0 且 L2 某簇命中 ≥3 → 该行业
3. **两簇皆强**（如既有 `package.json` 又有 `contract/`）或 **皆弱** → `generic-tasks` 派生，**绝不硬选**
4. 每条判定必须带 `evidence[]`（具体文件/目录名），**展示给用户**——猜错时 3 秒能纠正

**置信度**

| 情况 | 置信 | 表现 |
|---|---|---|
| L1 ≥3 且 L2 一致 | ≥0.85 | 直接给方案 |
| L1 ≥2 或 L2 ≥3 | 0.6–0.85 | 给方案 + 说明依据 + 提一个备选可能 |
| 其他 | <0.6 | 明确说"不确定"，给 `generic-tasks` |

### 形态判定

| 形态 | 特征 | 处置侧重 |
|---|---|---|
| **人写堆积型** | `datedNameRatio > 0.3`，`xxx_20261015.md`、`最终版_v2.md`、`报告_终版.md` 遍地 | 按主题归并 + 台账吸收一次性产物 |
| **agent 增殖型** | `specs/<NNN>-*/{spec,plan,tasks}.md`、`docs/features/*/` 成组出现 | 按 feature 收束，保留最新一代，旧代归档 |
| **混合** | 两者都有 | 分目录处置：堆积分区归并，增殖分区保留结构只清旧代 |

## 二、六槽骨架（任何行业都按这个填）

| 槽 | 回答 | 缺了会怎样 |
|---|---|---|
| ① 设计 | 这东西**是什么**、为什么这么设计 | 后来人反复重新推导 |
| ② 环境 | 它**在哪儿跑**、怎么搭起来 | 换个机器就卡住 |
| ③ 操作 | **照着怎么做**（可执行 + 每步判据） | 只能靠找历史记录拼步骤 |
| ④ 台账 | **发生过什么**（一个事件一行） | 一次性产物无处可去，继续堆积 |
| ⑤ 专项 | 横切多个主线的专题 | 横切内容散落各处 |
| ⑥ 待办 | **还没做什么** | 未完成事项只存在于对话里 |

**规则**：⑥ 必 1 份；⑤ 可 0 份；总数 >7 就合并；<4 通常是漏了 ④ 或 ⑥。

**归属口诀**：是什么→①，在哪跑→②，照着做→③，发生过→④，横切→⑤，没做→⑥，都不是→archive。

## 三、默认集

每份都要写出「管什么 / 不管什么（去哪查）」——这是防止再碎片化的关键，也是权威文档之间的路由表。

### A. software-delivery（交付型软件系统：To-B、多环境、有部署）

| # | 文档 | 管什么 | 不管什么 |
|---|---|---|---|
| 1 | 系统设计 | 架构、数据流、技术栈、ADR、架构级风险 | 部署步骤 → 2 |
| 2 | 环境部署 | 每套环境从零搭建、升级、备份回滚、验收 | 业务操作 → 3 |
| 3 | 使用与操作 | "照着能做"的业务流程与排障 | 架构 → 1 |
| 4 | 历史台账 | 逐环境/逐版本的实施记录、版本谱系、跨环境教训 | 操作步骤 → 3 |
| 5 | 专项设计 | 权限/审批/同步等横切专题 | 部署 → 2 |
| 6 | 待办 | 唯一挂账台账（P0–P3） | 已完成 → 4 |

> 有按模块增长的测试文档时：单列 `test-docs/`，**一模块一份，不合并**（模板：范围/用例/执行史/缺陷台账/未闭环/证据索引/复测指引）。

### I. generic-tasks（混合 / 不确定）

不是固定清单，而是**从目录结构反推任务域**：

1. 看 `signals.names.topDirs` 与各目录文件数
2. 每个"聚集了 ≥5 个文件、且主题可命名"的目录 → 提一个域文档
3. 加上 ⑥ 待办（必 1）与 ④ 台账（若有实施记录/证据类目录）
4. 域数控制在 3–6；超出就合并同类

输出形如：「域1 = 硬件/固件（`hw/` 32 文件）、域2 = 供应链（`supply/` 18 文件）、域3 = 售后（`aftersales/` 11 文件）+ 待办」。

## 四、未知行业：四步派生（永不"不支持"）

1. **填 ①②③**：是什么 / 在哪跑 / 照着怎么做（③ 必须可执行 + 每步判据）
2. **填 ④**：找出这个行业"一个事件一行"的载体（软件=部署记录、内容=发布台账、法律=事务台账、研究=实验记录、运维=记录表单）。**游离的一次性文档往这里收。**
3. **填 ⑤⑥**：横切专题（可 0）+ 唯一待办台账（必 1）
4. 校验：>7 份合并；<4 份查是否漏了 ④ 或 ⑥

## 五、agent 文档（可选，默认不动）

只在 `scan` 的目录里检测到 `AGENTS.md` / `CLAUDE.md` / `.cursor/rules` / `skills/` 时，加**一句可选追问**（不增加选项）：

> 我发现了 `AGENTS.md`（+N 个 scoped）。要不要一并纳入收束范围？（可选，默认不动）

检测不到就**一个字都不提**——agent 文档对很多人可选，主动建议创建反而制造碎片。
